# Lead figures

**Date:** 2026-10-29

## Problem

Of 194 blog posts, eight had an image. A designer's blog with no visual component reads as a gap. Most of those posts are short notes (more than half run under 250 words), and a picture on top of a 150-word answer would outweigh the answer.

## Decisions

- **Figures carry the argument.** A diagram, sketch, or redrawn slide that does part of the explaining. No decorative heroes, stock photography, or AI illustration.
- **Essays only.** Roughly, posts over 700 words, and only where a figure makes sense. Short notes stay text-only. Backfill runs recent first: this year's long posts, then older long posts ranked by traffic.
- **The figure lives in the body, where the argument needs it.** It is not a separate hero above the title, and it is not repeated. The optional `leadFigure` front matter field points at the one figure that stands for the post (see [authoring.md](../../authoring.md#optional)).
- **The homepage doesn't change yet.** It renders posts in full, so body figures already appear there. Revisit excerpts or page size once five or six essays have figures.
- **OG cards don't change yet.** At LinkedIn's ~128×72 feed size a figure is illegible, which is why the [dark card](2026-10-09-og-dark-card-design.md) is title-first. A low-contrast silhouette under the card's title is logged in `ideas.md` to try once several posts have lead figures.

## House style

Established on two figures: the three-horizons landscape in [Teaching a product team to do discovery](../../../src/posts/2026/2026-10-28-teaching-a-product-team-to-do-discovery.md), redrawn from a 2022 Cayuse slide that used a photo of a craggy ridge, and the diamond cloud in [Many little diamonds](../../../src/posts/2026/2026-10-09-many-little-diamonds.md), built on the frying-pan shape from the 2022 single-diamond post. A third, the device-as-spine flowchart in [Arguing with the agent](../../../src/posts/2026/2026-09-30-arguing-with-the-agent.md), carries the same rules into a diagram of states and arrows. A fourth, the benefit–concept–detail figure in [Prototyping in a regulated environment](../../../src/posts/2026/2026-08-27-prototyping-in-a-regulated-environment.md), puts the diamond cloud on a timeline: wild exploration converging onto a dashed freeze line, then a single bar of detail under scrutiny. A fifth, the craft bottleneck in [How do you raise the level of craft?](../../../src/posts/2026/2026-07-30-how-do-you-raise-the-level-of-craft.md), is a channel from designed to shipped whose pinches are named from the post's failure modes; the bottleneck is marked only by its red walls, with no label. A sixth, in [Toward coordinated experience](../../../src/posts/2025/2025-07-27-toward-coordinated-experience.md), stacks a fragmented three-step workflow over a coordinated one. A seventh, in [The complaints that wouldn't go away](../../../src/posts/2026/2026-07-24-the-complaints-that-wouldnt-go-away.md), sets the design system in Figma over the design system in code and shows each kind of drift once. A before-and-after version, with a fixed half where every component matched, was dropped: the fix wasn't illuminating, and the drift was the point. An eighth, in [Agentic AI doesn't make human interfaces go away](../../../src/posts/2026/2026-04-20-agentic-ai-doesnt-make-human-interfaces-go-away.md), draws the interface as a magnifying glass held over the same objects the agent's tools just changed. Two earlier drafts taught what not to do. An interface drawn as a box holding a small copy of the objects read as a second set of objects. And an empty box for the agent's tools read as empty, not as tools, so they became separate pill-shaped actions, one in use and two idle. A ninth, in [This is what we were waiting for](../../../src/posts/2026/2026-06-15-this-is-what-we-were-waiting-for.md), is a Sankey of what a team learns from customers, Then and Now. It shows how much of that is lost to negotiation, drift, and bugs or parked in a backlog, and how much of the work along the way is UX's own. A tenth, in [Designers who ship](../../../src/posts/2026/2026-06-03-designers-who-ship.md), is a range map, the way a field guide shows where a species lives. Design sits in the middle with its five neighbors around it, a dashed edge for the designer's range before, and a red range for now that pushes hardest into Metrics, Data, and Code. One is a place and the others are ideas, so they'll never look like twins; type, accent, tone, and the dark-mode rules are what make them a family.

- **2:1, a standalone SVG shown with `<img>`.** The first version was inline, so it could use the page's tokens and fonts directly. But the RSS feed carried the SVG without the site stylesheet, which made every gradient stop and label default to black, and the path data cluttered the markdown and shipped inside the homepage HTML on every visit. As an image file it caches, shows up in feed readers, and keeps its styling local to the figure. `eleventy-img` passes SVG through untouched (`svgShortCircuit`), since rasterizing would lose the dark-mode styles.
- **Fill the 2:1 frame by rearranging, not by shrinking it.** When content runs in a single line, restack it first: the coordinated-experience comparison started as two panels side by side, which left a 2:1 frame mostly empty, and became two rows, one above the other, with titles at the left. Use a shorter frame only when the content can't be rearranged.
- **A figure carries its own styles.** An SVG loaded as an image can't see page CSS, load web fonts, or fetch anything else. Its `<style>` copies the site tokens it needs (any of `--text-color`, `--text-color-light`, `--content-background-color`, `--link-color`) and derives the figure's own colors from them. `pnpm run test figure-tokens` fails when a copy no longer matches `jonplummer.css :root`. The site follows the OS color scheme with no manual toggle, so the figure's `light-dark()` switches when the page does. Gradient stops take classes (`stop-ridge-mid`) rather than `stop-color="var(…)"`, which is unreliable as a presentation attribute.
- **Figures are generated, not hand-edited.** Each one is a module in `scripts/figures/` with fixed control points and a seeded random generator, so it regenerates identically. `pnpm run generate-figures` writes the SVG, which gets committed. Labels are converted to outlines at that point, from fontsource's static Big Shoulders 700. fontkit can't make a bold instance of the variable WOFF2 the site serves. The build and the tests never load fontkit or the font, so an upgrade to either can't break them; it only matters when a figure is regenerated.
- **Landscapes use atmospheric perspective.** Contrast falls off with distance. Light mode is daylight haze, with the near ridge darkest. Dark mode is dusk: the near ridge goes darker than the content field and the far range glows toward the horizon. Mixing ink into the field for dark mode made the near ridge the brightest thing on the page, so ridges carry their own dark values (`--ridge-*` in the figure's style). Each ridge needs a clear step from what's behind it in both modes; the dark middle ridge went from 29% to 20% lightness after it vanished into a 30% haze.
- **Dark mode sinks the ground and lifts what matters.** In the landscape the near ridge is the ground; in the diamond cloud the textbook double diamond is, and it goes to 12% lightness, a shadow below the 22% page. The shapes the figure is about stay strong against it: light grey and accent in dark mode, dark grey and accent in light.
- **`light-dark()` takes colors only.** An opacity that differs by mode has to live in the color, as `color-mix(in oklch, <color> 26%, transparent)`. A `light-dark()` on `fill-opacity` is invalid, and the browser silently drops the whole declaration.
- **Translucent shapes need more alpha over a dark ground.** The cloud's unlabeled pans are 26% in light and 55% in dark. At 26% they sank to near-invisible wherever they crossed the dark double diamond.
- **A stronger shape never sits under a weaker one.** Draw the ground first, then the crowd, then the callouts. Callouts are opaque, so the ground can't show through them.
- **Emphasis goes to the decisive moment, not to a winner.** Marking one pan per phase as "the chosen one" overstated how tidy exploration is. In the benefit–concept–detail figure every exploratory pan is light, including the big concept pan that stops just short of the freeze line; the only strong pan is the small one beside it that actually crosses.
- **Let shapes make the outline.** A cloud reads as a shape when a few big pans on the centerline set its ends (the benefit pan's handle opens it; the concept pans' points close it) and the rest fill in. Ninety small pans packed into an ellipse lost the wildness; a drawn ellipse behind them looked like a container. Big pans in one figure should differ in size.
- **Not every shape needs a label.** Label the few the post names and give them the strong tone, so a reader can tell which shape a label belongs to; the rest stay faint. Labels don't get halos: a halo in the page color showed as a grey outline wherever a label crossed the dark-mode ghost, and full-strength text reads fine over the faint shapes without one.
- **The accent marks what the post is about.** In the horizons figure the far range and its label take `--link-color`; in the cloud, the "Find the benefit" pan does, because it's the diamond Neeman skips. Mix the dark-mode accent in `oklab`; `oklch` swings red-into-grey through purple.
- **Labels use the post's own words.** "Horizon 1: Ship," not the slide's "late this release" – the figure and the text beside it have to agree. Big Shoulders bold at 56 viewBox units, which renders near 12px at phone width; that is the floor. Place each label on or just above the thing it names, close enough that it can't be read as belonging to a neighbor. A shape too small to carry a label below it (the cloud's "Wording") gets it to the side. No leader lines. Use names a reader can't mistake for an error: "Label" read as a placeholder, "Wording" didn't.
- **Alt text is a substitute, not a description.** It has to give a reader who can't see the figure what the figure gives everyone else, at that point in the post. So the test is the prose around it: if the text already makes the figure's point, the alt is empty, `![](…)`, however elaborate the drawing. Every figure so far passes that test. The horizons list explains the three horizons; the diamond cloud's points (single diamonds everywhere, at every size; the double diamond never matched practice; finding the benefit is a diamond of its own) are all in the surrounding paragraphs. A description of the drawing would only repeat them, worse. markdownlint's MD045 can't tell a deliberate empty alt from a forgotten one, so put `<!-- markdownlint-disable-next-line MD045 -- reason -->` above it. When a figure does make a point the text doesn't, the alt states that point, not what the figure looks like.
- **Flowcharts follow Jon's flowcharting rules.** A box is a state, an arrow is how you get to or leave it, a diamond is logic you pass through. Arrows get rounded corners, which makes a line easier to follow through a turn. A line that carries attention is thick, runs straight down whichever lane holds attention, and crosses between lanes only in the gaps between rows, with the same smooth pair of turns each way. Smoothness beats entering a box from the side: a side entry squeezed into a short gap made a jagged S. When one lane is in charge, it's the emphasized one – wider boxes, a stronger lane, the full-strength label – and the other lane is a step quieter in every state, so the hierarchy holds even where the quiet lane has the user's attention. A decision sits in the lane that has the information, with its label just outside that lane on the diamond's row.
- **A barrier is a question, not a broken arrow.** Where the user has to know to go somewhere else, the line from the step stops, a red "?" at label size sits in the gap, and a short red stub reaches the next step, which goes quiet because it's out of reach. Red barbs on a broken line read as damage; the question mark says what the user is left with. Steps the system connects get a plain solid line, and a capability the step offers in place is a module drawn inside that step.
- **Missing things are red outlines.** A component that's absent on one side is a dashed red outline where it should be. A missing variant is a page-colored cell with a heavy solid red border, because dashes at that size broke into specks at phone width. Things that should match and don't get a red "≠" between them. Big Shoulders has no "≠", so the figure draws it: two bars and a slash at about the labels' stroke weight. Before using a symbol as a label, check that the font has it; a missing glyph renders in a fallback font in the browser, and in the outlined SVG it would come out as nothing at all.
- **A magnifying glass really magnifies.** Under an opaque lens, the figure draws a clipped, scaled copy of the scene. So a line that crosses the rim jumps in position and thickness, the way it would under real glass. Keep any junction outside the lens, so a line visibly splits before its branches enter.
- **Sankey bands keep a flat top edge.** Width comes off the bottom, where each drain peels away. Steps on both edges read as a line changing weight, not as something being drawn off. Everything flows right. The only exception is an obvious loop, which gets a pointed tip where it arrives because a Sankey has no arrowheads to show direction. Overlap adjoining band segments by a unit, or a hairline seam shows where the width changes.
- **The same thing gets the same shape everywhere in a figure.** In a before-and-after, draw both rows from one template, so a drain, a pool, or a box sits in the same place with the same curves. Only widths and color differ.
- **Size a stretched shape's reaches on the page.** A radial map stretched sideways to fill 2:1 makes a reach toward the sides look almost twice as long as the same reach up or down. In the range map, an even push into Metrics, Data, and Code read as Metrics getting the lion's share until each reach was divided by its on-page stretch. Keep an edge that should read as one broad push convex, too: an outline offset from a lobed one inherits its dips.
- **Color means one thing per figure.** In the Sankey, red is UX's own work and nothing else. A whole red row claimed too much. Coloring only UX's segments let the color show the change: in Then, UX's red stops at the spec; in Now, it reaches the product.
- **Images have edges.** The figure can stop flat at its frame; it doesn't need to fade into the page.

## Where things live

- `scripts/figures/<name>.js` – one module per figure, exporting `output` and `render()`. `figure-utils.js` holds the seeded random generator, the ridge generator, label outlining (left, centered, or right-aligned), rounded-corner polylines, and the token reader. `generate-figures.js` runs every module.
- `src/assets/images/YYYY/MM/<name>.svg` – the generated file, committed. It carries a "Generated by scripts/figures/" comment, which is how `figure-tokens` finds it.
- `scripts/test/figure-tokens.js` – compares each generated figure's token copies with `jonplummer.css :root`. It doesn't regenerate the figure, so the test needs no fontkit or font.
- `scripts/test/frontmatter.js` – `leadFigure` must be a path under `/assets/images/` that exists and that the post body shows.
- [Figma catalog](https://www.figma.com/design/ailr6PhPXO0SHSuWdZx31S) – every figure as editable vectors, one row per post, newest first, light and dark side by side. It's for reworking a figure by hand. The SVG in the repo stays the source of truth, so carry any hand change back into the figure's module. When a post gets a new figure, run `pnpm run flatten-figures <name>` and import `.cache/figma-figures/<name>-light.svg` and `-dark.svg` into a new row in the catalog. Figma's SVG import ignores CSS, so the flattener resolves every color to plain hex first. Then bind the new layers to the catalog's variables, so the colors there stay named the way the CSS names them:
  - **Site** (Light and Dark modes) copies `jonplummer.css :root`: `text-color`, `text-color-light`, `content-background-color`, and `link-color`.
  - **Figures** (Light and Dark) holds the colors figures mix from those tokens. Mixes that more than one figure uses are `mix/ink-70`, `mix/ink-45`, `mix/ink-30`, `shared/pan`, and `shared/ground`; colors only one figure uses are grouped as `<figure>/<class or custom property>`. Each variable's description gives the CSS expression it comes from.
  - **Figure strokes** holds stroke widths, as `<figure>/<class>`.

  Each Light or Dark frame sets its mode for both color collections, and its own fill is `content-background-color`. Bind a layer to the Site token when its class is a plain `var(--…)`. When the class is a mix, reuse a Figures variable whose values match, or add one. When `jonplummer.css` tokens change, update the variable values; the bound layers follow.
